### 八、MySQL 高频必考（索引 / 事务 / 锁 / SQL 优化）

#### 索引

##### M1. 为什么 InnoDB 用 B+ 树而不是哈希、B 树或跳表？

【面试回答】四个候选各有死穴：哈希等值查询 O(1) 最快，但不支持范围查询和前缀匹配、有冲突退化，而业务里大量是 order by/区间扫描；二叉树/AVL 树高随数据量增长快，磁盘 IO 次数等于树高不可接受；B 树非叶节点也存数据，单页能放的 key 变少、树更高，且叶子不串联，范围查询要中序回溯。B+ 树把数据全放叶子、非叶只存 key+ 页指针，单页容纳更多分支使三棵树就能存两千万级行（16KB 页、主键 bigint 8 字节估算），叶子层双向链表让范围查询变成顺序扫页。哈希能力由 InnoDB 自适应哈希索引内部补充，不需用户设计。

【一句话背诵】全在叶子 + 叶子拉链表：树矮省 IO、范围能顺扫，这是选 B+ 的两条命门。

##### M2. 聚簇索引和二级索引回表是什么？怎么避免回表？

【面试回答】聚簇索引叶子存整行，InnoDB 里就是主键树（无主键选第一个非空唯一索引，再没有就隐式 row_id）；二级索引叶子存「索引列值 + 主键」，所以走二级索引查到主键后还要再进聚簇树取整行，两次树查找即回表。避免回表的手段是覆盖索引：select 的列全在二级索引里（含主键），Extra 显示 Using index 就不回表。实践：列表页只查必要列、别 select *；把高频过滤与展示列做成联合索引（order_id, user_id, status, amount）实现覆盖。面试延伸：回表代价随随机 IO 计，所以二级索引命中行数比例高时优化器宁走全表——这是"索引失效"错觉的一个来源。

【一句话背诵】二级索引叶子只有主键，取整行要回表；让索引覆盖查询列即可免回表。

##### M3. 联合索引的最左前缀原则？为什么范围查询后面用不上索引？

【面试回答】联合索引 (a,b,c) 的 B+ 树先按 a 排序，a 相同才按 b，b 相同才按 c。查询条件带上 a、a+b 都能利用有序性定位；跳过 a 直接查 b 时，b 在树上是全局无序的，只能扫描，所以用不上。范围查询打断有序：a=1 and b>10 and c=5 里 c 用不了索引，因为在 b 的范围内 c 不保证有序——c 只能当过滤条件在 server 层判（旧版本叫 Index Condition Pushdown 可在索引层过滤，减少回表，可作加分补充）。经验设计：等值列放前、范围列放后、排序列紧随等值，能把 filesort 消掉。

【一句话背诵】索引按 a→b→c 逐层有序，断了前面的等值就废；范围列之后的列退化为过滤。

##### M4. 哪些情况会导致索引失效？

【面试回答】常见八类：对索引列做函数或运算（where year(t)=2026、id+1=5）；隐式类型转换（varchar 列传数字，内部对列套 CAST 函数）；前导模糊 like '%xx'（'xx%' 可用）；字符集/排序规则不一致导致跨表比较弃索引；联合索引不满足最左；优化器判定回表成本高于全表（低区分度列如性别、命中行数占比大）；not in / not exists / != 这类否定条件通常难走索引；order by 方向与索引不一致。定位靠 EXPLAIN 看 type（const>range>ref>index>ALL）、key、rows、Extra（Using filesort / Using temporary / Using index）。

【一句话背诵】套函数、隐式转、左模糊、断最左、区分度低、否定条件——EXPLAIN 的 type 和 Extra 说话。

##### M5. 主键为什么推荐自增而不是 UUID？

【面试回答】InnoDB 数据按主键顺序物理存放。自增主键让新行总是追加到最右叶子页，顺序写、页分裂少、空间紧凑，也使我项目里"主键倒序取最近数据"成为可能（用 id 降序代替时间列排序，避免 filesort）。UUID 无序，插入位置随机，导致目标页满则分裂、写放大、缓存命中率低、碎片多。折中方案：用有序变体（Snowflake 趋势递增 ID、UUIDv7）或数据库自增 + 业务码分离。答题落点：页分裂与局部性，不是"性能玄学"。

【一句话背诵】自增=顺序追加少分裂；UUID=随机插疯狂页分裂，要用就用趋势递增 ID。

#### 事务

##### M6. ACID 分别靠什么机制保证？

【面试回答】原子性靠 undo log：回滚日志记录反向操作，事务失败按它撤销。持久性靠 redo log：WAL 先写日志再刷脏页，崩溃后重放日志恢复已提交改动（两阶段提交保证与 binlog 一致）。隔离性靠锁 + MVCC：写用锁互斥，读靠多版本快照不加锁。一致性是目标而非机制——由前三者加上约束/唯一键/业务逻辑共同达成。面试标准表述："AID 是手段，C 是目的"。

【一句话背诵】undo 管原子、redo 管持久、锁+MVCC 管隔离，一致性是三者共同服务的结果。

##### M7. 并发事务有哪几类异常？隔离级别怎么对应？

【面试回答】三类脏读/不可重复读/幻读加两类丢失更新：脏读读到未提交数据（读未提交才会）；不可重复读指同一事务内两次读到已被提交的 UPDATE 结果（读已提交可解）；幻读是两次范围查询多出/少掉整行（严格解需可重复读以上）。InnoDB 默认 RR，并通过间隙锁 + 快照读基本抑制幻读（不是彻底：当前读与快照读混用会出现"幻影行"经典坑）。Oracle 默认 RC，SQL 标准默认 RR。RR 还带来一个业务问题：读到旧快照导致更新丢失，实践常配合乐观锁 version 字段解决——正是我实习项目里任务领取用 version 乐观锁的原因。

【一句话背诵】脏读=未提交，不可重复=已提交改值，幻读=行数增减；InnoDB RR 靠间隙锁压制。

##### M8. MVCC 的实现细节？ReadView 在 RC 和 RR 下有何不同？

【面试回答】每行隐藏两列：trx_id（最后修改事务号）和 roll_pointer（指向 undo 版本链）。快照读时生成 ReadView：记录当时活跃（未提交）事务 id 列表、最小 id、创建者 id、以及分配的上界。可见性判断：trx_id < 最小→已提交可见；在活跃列表内→不可见；≥ 上界→创建后新事务，不可见；否则看是否在活跃列表中，不在则可见。沿 undo 链找到第一个可见版本。差异在生成时机：RC 每条 select 都新建 ReadView（所以能看到别的新提交，不可重复读），RR 只在事务第一次快照读时创建并复用（整个事务看到同一快照）。

【一句话背诵】版本链 + ReadView 判可见；RC 每次读都换眼镜，RR 一副眼镜戴到底。

#### 锁

##### M9. InnoDB 的锁有哪些？行锁是怎么加的？

【面试回答】按粒度分全局锁、表级锁（意向锁 IS/IX 用于快速判断表内有行锁、MDL 元数据锁、AUTO-INC 锁）、行级锁。行锁三种形态：记录锁锁单行、间隙锁锁两行之间开区间不锁行本身、临键锁（Next-Key Lock）= 记录锁 + 前向间隙，是 RR 默认加锁单位；主键等值且命中唯一行时降级为记录锁。关键原则：锁是加在索引上的——不走索引的更新会锁住扫描经过的所有行（最坏等价表锁效果），所以 update 必须带索引条件。意向锁的必要性：表级锁与行级锁共存时，避免检查全表每行是否有锁，O(1) 判定冲突。

【一句话背诵】行锁分记录/间隙/临键，加在索引上；不走索引的写会把扫描行全锁住。

##### M10. 死锁的产生条件与排查预防？

【面试回答】经典场景：事务 A 锁 1 更新 2，事务 B 锁 2 更新 1，交叉等待。四个必要条件：互斥、持有并等待、不可剥夺、循环等待——破坏任一即可预防，工程常用"按固定顺序访问资源"（如按主键升序批量更新）破坏循环等待。运行期 InnoDB 用 wait-for graph 检测，发现环则回滚代价小的事务（innodb_deadlock_detect），报 1213；另一种是锁等待超时 innodb_lock_wait_timeout=50s。排查：SHOW ENGINE INNODB STATUS 看 LATEST DETECTED DEADLOCK、performance_schema.data_locks/data_lock_waits 看现场。预防组合拳：事务尽量短小、更新走索引、热点行用排队或改成 Redis 预扣、高争用场景考虑乐观锁替代悲观。

【一句话背诵】交叉等待成环；定序访问破环、走索引少锁行、短事务少持有，现场看 data_lock_waits。

##### M11. 乐观锁和悲观锁怎么用？

【面试回答】悲观锁假定冲突频繁，先锁再操作：select ... for update（当前读加临键锁），适合库存扣减这类强一致热点，代价是并发被串行化。乐观锁假定冲突少，读时不锁，写时校验版本：update ... set stock=stock-1, version=version+1 where id=? and version=?，影响行数为 0 表示被抢改，重试或返回失败。它天然防丢失更新（对应"更新丢失"异常）且吞吐高，缺点是极端争用下重试风暴。选型依据冲突率：<20~30% 用乐观，更高用悲观或减小临界区（分段库存、异步队列）。我实习项目里志愿者领取任务用 version 乐观锁，就是为了防止并发派单把同一地址分配两次。

【一句话背诵】悲观先锁后动，乐观改时比版本；冲突率低用乐观，高就悲观或拆小临界区。

#### SQL 优化

##### M12. EXPLAIN 主要看哪几列？慢查询怎么系统优化？

【面试回答】EXPLAIN 看六项：type（访问类型，const/eq_ref/range/ref 可用，index/ALL 要警惕）、key（实际用的索引）、key_len（用到联合索引的字节数，判断是否只用到前缀）、rows（预估扫描行数）、filtered、Extra（Using index 覆盖、Using index condition 下推、Using filesort 内存/磁盘排序、Using temporary 临时表，后两个是优化目标）。优化路径固定五步：定位（慢查询日志 long_query_time + pt-query-digest）→ 看计划 → 改索引/改 SQL（等值在前、避免列上函数、覆盖索引、缩小结果集）→ 验证 → 兜底（分页改游标、大事务拆小、必要时缓存或分库）。

【一句话背诵】type/key/key_len/rows/Extra 五件套；定位-看计划-加索引-改写-验证，别跳步。

##### M13. 深分页为什么慢？怎么优化？

【面试回答】limit 1000000,20 要真正取前一百万零二十行再丢掉前一百行：聚簇索引侧代价接近百万级，且这大量行还参与排序与回表，网络虽只发 20 行但引擎成本已花掉。优化三法：一是游标/书签法——记住上一页最后主键，改 where id > last_id order by id limit 20，走索引范围扫，代价恒定；二是延迟关联——先 select id 在覆盖索引上分页拿到 20 个主键，再 join 回表取整行，把百万次回表压成 20 次；三是业务侧禁止跳页，产品形态改为"上一页/下一页"或加时间维度过滤。我项目在亿级传感器表上正是用主键倒序 + 条件收敛来避免大扫描，同理适用。

【一句话背诵】offset 白扫是根因；改成"记住位置"的游标法或先取 id 再回表的延迟关联。

##### M14. 亿级大表上做 DDL（加索引）要注意什么？

【面试回答】直接 alter table add index 会重建整张表的索引结构，长事务锁表、撑爆磁盘余量、并阻塞写入，生产上基本不可接受。方案：MySQL 8 的 ALGORITHM=INPLACE 加索引不锁写但仍有 IO/复制延迟压力；更稳的是 Online DDL 配合 gh-ost/pt-online-schema-change 影子表 + binlog 增量回放 + 原子 rename。另外从工程实践上，我在初始化阶段采用"先灌数据、后建索引"：省去边写边维护 B+ 树的多次页分裂与日志开销，实测单次大表建索引时间显著压缩。答题要点：锁行为、空间、复制延迟、分阶段建库顺序。

【一句话背诵】大表加索引靠 Online DDL/影子表；建库时先灌数后建索引，避免边写边分裂。
