### 九、Redis 高频必考（数据结构 / 持久化 / 缓存问题）

#### 数据结构与底层编码

##### R1. Redis 常用类型及底层编码？

【面试回答】String：int/embstr（≤44 字节）/raw，setk 计数、缓存对象、分布式锁、INCR 限流。Hash：元素少用 listpack（紧凑内存、顺序扫快），超阈值转 hashtable（编码字典），适合存对象字段做局部更新。List：quicklist = 双向链表串起多个 listpack，LPUSH/RANGE 两端 O(1)，做消息列表、最新时间线。Set：intset（整数有序紧凑）或 hashtable，做去重、共同好友、标签交集（SINTER）。ZSet：元素少先 listpack，否则 skiplist + hashtable 双结构——跳表按分数 O(logN) 范围取，哈希 O(1) 取 rank，榜单核心。另有 bitmap（签到/活跃）、HyperLogLog（UV 去重估算 12KB 固定内存，误差 0.81%）、Stream（带 ID 与消费组的消息流）、GEO（基于 ZSet 的地球坐标）。

【一句话背诵】每类型都有"小数据省内存编码 + 大数据性能编码"两副面孔，ZSet = 跳表 + 哈希。

##### R2. 为什么 Redis 单线程还这么快？6.0 为什么要加多线程？

【面试回答】快源于三点：纯内存操作（亚微秒级）、单线程省去锁竞争与线程上下文切换、IO 多路复用 epoll 单循环管上万连接。瓶颈不在 CPU 而在内存和网络带宽。6.0 引入的多线程只负责网络 IO 的读解析与写回（io-threads），命令执行仍是单线程，因此无需考虑并发安全，也不会破坏原子性。这解决的正是"大 value/高并发下网络读写成为瓶颈"的问题，官方文档建议 4~6 个 IO 线程。

【一句话背诵】单线程避开锁与切换，靠 epoll 撑并发；6.0 多线程只搬网络，执行仍单线程。

#### 持久化

##### R3. RDB 和 AOF 的原理、优缺点与选择？

【面试回答】RDB 是某个时刻的全量二进制快照：fork 子进程把内存写盘，靠操作系统的写时复制（COW）保证父进程继续服务不阻塞（但写密集时页复制有开销、大堆 fork 本身耗时）。配置 save 900 1 这类条件或 save 手动触发，恢复直接 load，文件紧凑适合备份与冷启动。缺点：两次快照之间的数据宕机丢失，fork 瞬间抖动。AOF 是追加写命令日志，落盘策略 appendfsync always（每次写 fsync，最安全最慢）/ everysec（默认，最多丢 1 秒）/ no（交给 OS）。体积大、恢复慢，所以有 AOF rewrite：后台按当前数据生成最小命令集重写文件，期间新写入进 rewrite buffer 追加到新文件。生产标配：RDB + AOF 混合持久化（redis 4+ aof-use-rdb-preamble），AOF 重写时先写 RDB 体再追加增量日志，兼顾恢复速度与数据安全。

【一句话背诵】RDB 快照 fork+COW 备份快会丢一段；AOF 记命令 everysec 折中；混合持久化取两者之长。

##### R4. Redis 宕机后怎么恢复？主从与哨兵、Cluster 怎么配合高可用？

【面试回答】恢复顺序：先试 AOF（数据新），有 RDB 无 AOF 用 RDB，都没有就空库（缓存场景可接受）。高可用三档：主从复制——从节点全量同步（Master 生成 RDB 快照传输 + 缓冲区补增量，注意 repl-buffer 太小会反复全同步触发复制风暴）后转增量，只解决读扩展与数据冗余，从节点不能自动顶上；哨兵 Sentinel——多节点监控主节点心跳与主观/客观下线（quorum 判定），自动故障转移选新主，客户端向哨兵要地址，一主一从都可能脑裂，需配 min-replicas-to-write 等参数；Cluster——16384 个 slot 分片到多主多从，客户端 MOVED/ASK 重定向，支持水平扩容与故障转移，代价是不支持跨 slot 事务与复杂多 key 操作。面试落点：先问数据量与读写比例，再决定"主从+哨兵"还是 Cluster。

【一句话背诵】全量同步靠 RDB + 复制缓冲；哨兵保可用，Cluster 保扩展，两者都做故障转移。

#### 缓存问题

##### R5. 缓存穿透、击穿、雪崩的区别与解法？

【面试回答】穿透：查不存在的数据，缓存永远不命中，每次都打 DB——恶意用随机负数 id 可放大。解法：缓存空值（短 TTL 几十秒）、布隆过滤器前置拦截（注意有误判率、不支持删除，可用 Counting/Scalable Bloom）、参数校验。击穿：单个热点 key 过期瞬间大量并发同时打到 DB。解法：互斥锁/singleflight 只放一个线程回源其余等待、热点 key 逻辑过期不真删（value 里带过期时间，异步重建）。雪崩：大批 key 同一时刻集体失效或 Redis 整体宕机。解法：TTL 加随机抖动打散、多级缓存（本地 Caffeine + Redis）、限流降级兜底、保证 Redis 高可用。三者的关键区分：穿透=查没有的东西，击穿=一个 key 过期，雪崩=一片 key/整个服务挂。

【一句话背诵】空值+布隆防穿透，加锁/逻辑过期防击穿，TTL 打散+多级缓存防雪崩。

##### R6. 如何保证缓存与数据库一致性？

【面试回答】主流方案 Cache Aside（旁路缓存）：读时先查缓存，未命中读 DB 再写缓存；写时先更新 DB 再删除缓存（不是更新缓存——避免并发写导致旧值覆盖新值，也避免写一个没人读的复杂值）。先删缓存再更新 DB 的问题是：删除后、DB 更新前，并发读会把旧值填回缓存。先更新 DB 再删缓存也有小概率不一致（读到旧 DB 值的并发线程恰好在删除之后回填），所以工程上再叠两层兜底：延迟双删（更新后稍等再删一次，等慢读回填完成）、订阅 binlog（Canal 伪装 MySQL slave 拉 binlog 异步删缓存，把"删缓存"从业务代码解耦，可靠性最高）。面试标准结论：缓存与 DB 只能做到最终一致，要求强一致就别用缓存或加分布式锁把读写串行化（代价大，很少这么干）。

【一句话背诵】旁路缓存"更 DB 删缓存"，兜底靠延迟双删或 Canal 订 binlog，本质只保证最终一致。

##### R7. Redis 分布式锁怎么实现？有哪些坑？

【面试回答】最小实现：SET key unique-value NX PX 30000——NX 保证互斥、PX 保证超时自动释放（防死锁）、value 存请求唯一标识。释放必须用 Lua 脚本原子地"比对 value 再删除"，否则会删掉别人的锁（自己超时后别人拿到锁的场景）。三个坑与对策：一是业务未执行完锁先过期——看门狗 watchdog（Redisson 默认 30s 锁、每 10s 续约）；二是锁粒度：key 要设计成资源维度（lock:order:{id}）而非全局；三是 Redis 主从异步复制导致的丢锁：主节点写入锁后未同步就宕机，从升主后锁不存在，理论上要 Redlock（向 N 个独立实例多数派加锁），但实现复杂且受时钟漂移影响，学术界有争议。务实答案：一般业务 Redis 单实例/主从 + 唯一 value + Lua 释放足够；涉及钱的关键路径用 DB 唯一约束兜底（我项目里就是靠数据库唯一索引保证同一地址不被重复分配，锁只做效率优化而非正确性唯一来源）。

【一句话背诵】SET NX PX + 唯一值 + Lua 释放；看门狗防超时，正确性最后靠唯一约束兜底。

##### R8. 大 key 与热 key 怎么处理？

【面试回答】大 key（单个 value 过大，如百万元素 ZSet、几 MB String）：阻塞网络与 IO、删除时卡主线程、迁移倾斜。定位：redis-cli --bigkeys 采样、rdb-tools 离线分析。处理：拆分（把大 Hash 按字段前缀分桶）、value 压缩、ZSet 分页取、scan 友好删除或 lazyfree 异步释放。热 key（单 key QPS 极高，如明星八卦、秒杀库存）：打爆单分片带宽与 CPU。处理：本地缓存 + 短 TTL 分摊（Caffeine 挡一层）、key 加随机后缀做多副本（读时随机选一副本，写时更新全部）、Cluster 迁移到独立分片并用副本读扩展。面试点：内存问题看大 key，吞吐问题看热 key，二者都不靠"加机器"简单解决。

【一句话背诵】大 key 拆 + 懒删，热 key 本地缓存挡或打散成多副本；一个是内存病，一个是带宽病。
