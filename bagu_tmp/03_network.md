### 十、计算机网络高频必考（HTTP/HTTPS / TCP）

##### N1. 从输入 URL 到页面展示，中间发生了什么？

【面试回答】DNS 解析（浏览器缓存→系统缓存→hosts→本地 DNS 递归→根/顶级/权威迭代，拿 IP）→TCP 三次握手（HTTPS 再叠加 TLS 握手）→发 HTTP 请求→服务器处理（可能经 CDN、负载均衡 Nginx、网关、后端应用）→响应→浏览器解析 HTML 构建 DOM、CSSOM，合成渲染树、布局、绘制；JS 阻塞解析需注意 defer/async。加分点：CDN 命中静态资源时直接走边缘节点；HTTP/2 多路复用让同域请求不必排队。这题的答法体现系统观，尽量按"网络层→服务端→前端渲染"三段讲清。

【一句话背诵】DNS→握手→请求→服务端链路→响应→构建渲染树，串三层讲。

##### N2. TCP 三次握手为什么是三次不是两次？

【面试回答】握手要同时确认双向通路可用。两次的问题：客户端 SYN 携带 seq=x，服务端 SYN+ACK 携带 seq=y，若只到两次，服务端无法确认"客户端收到了自己的 SYN"，服务的确认丢失后客户端已进 ESTABLISHED 发数据，服务端重发 SYN 会造成状态错乱；且两次握手会让历史失效的 SYN 请求（网络滞留后到达）直接在服务端建立半连接，被旧包重复建立连接浪费资源。三次里客户端第三次 ACK 带 ack=y+1，服务端由此确认自己的 seq 被对方正确接收，同时这个 ACK 能识别过期 SYN（客户端会 RST）。SYN 洪泛正是打第一次握手后服务端维持大量 SYN 队列（半连接队列），防御用 SYN Cookie。

【一句话背诵】三次才能双向序号互相确认，并让过期 SYN 无法单独建连；防 SYN 洪泛用 Cookie。

##### N3. 四次挥手与 TIME_WAIT 的作用？

【面试回答】关闭是全双工两个方向各自关：客户端 FIN→服务端 ACK（第一次、第二次，方向一确认）；服务端处理完剩余数据再发 FIN→客户端 ACK，因为服务端可能还有数据要发，ACK 和 FIN 不能合并，所以比握手多一次。TIME_WAIT 在主动关闭方停留 2MSL：一是保证最后一个 ACK 能重发（对端没收到 ACK 会重发 FIN，自己已关就无法应答）；二是让网络中残留的旧报文段自然消亡，防止同样的四元组新连接收到上一个连接的迟到包。高并发短连接服务器会堆积 TIME_WAIT，缓解：调内核参数复用（tcp_tw_reuse）、用长连接/连接池、客户端端口充足。

【一句话背诵】挥手各方向各两次因服务端 ACK 时还有数据；TIME_WAIT 等 2MSL 保重发与旧包消亡。

##### N4. TCP 怎么保证可靠传输？

【面试回答】五套机制协同：序号 + 确认（每字节编号、累积 ACK，收不到重传）；超时重传 RTO（RTT 动态估算，Karn 算法排除重发包干扰）与快速重传（收到 3 个重复 ACK 立即重传，不等超时）；滑动窗口做流量控制（接收方通过 rwnd 通告剩余容量，发送方不超过）；拥塞控制做网络侧调节——慢启动（指数增）、拥塞避免（线性增）、快重传、快恢复（乘性减），cwnd 与 rwnd 取小者为准；校验和 + 保留重传兜住损坏包。加分延伸：对比 UDP 无连接不保证但低延迟，实时音视频选择 UDP 自研可靠性（如 KCP/QUIC）；QUIC 用 UDP 做 0-RTT 握手、每流独立无队头阻塞，正是 HTTP/3 的地基。

【一句话背诵】序号 ACK + 重传保序不丢，双窗口管流量与拥塞，丢包路径靠快速重传提速。

##### N5. HTTP/1.1、HTTP/2、HTTP/3 的核心演进？

【面试回答】1.1：长连接复用 TCP（keep-alive）但请求必须排队——队头阻塞在应用层，浏览器只能靠分域名开 6 个并发连接硬凑；无状态、文本协议开销大。2.0：二进制分帧 + 单连接多路复用（多个流并发交错）解决应用层队头阻塞，HPACK 头压缩减重复头，服务器推送（实践效果差已冷遇）；但底层还是 TCP，一旦丢包整个 TCP 流上所有流都卡——传输层队头阻塞仍在。3.0/QUIC：换到 UDP 之上，每个流独立重传互不阻塞，TLS1.3 内嵌握手 0/1-RTT 建连，连接迁移用 Connection ID 不受换 IP 影响（移动网络关键）。演进主线一句话：把"阻塞"一层层剥掉——1.1 应用层排队→2.0 TCP 丢包阻塞→3.0 彻底解耦。

【一句话背诵】1.1 排队、2.0 多路复用但 TCP 队头、3.0 基于 UDP 流独立 + 0-RTT。

##### N6. HTTP 常见状态码与 GET/POST 区别？

【面试回答】状态码按位记：200 成功、204 无内容、301 永久重定向（SEO 权重转移）、302 临时、304 协商缓存命中未修改；400 参数错、401 未认证（没带或 token 失效，我后端在 JWT 过期时返回它，前端拦截器清会话跳登录）、403 已认证但无权限、404 资源不存在、429 限流；500 服务端异常、502 网关收到无效响应（后端挂了）、503 过载不可用、504 网关等后端超时。GET/POST：语义上 GET 幂等只读、可缓存、参数在 URL（长度受限、留历史，敏感信息不该用）；POST 非幂等、在 body。技术层面浏览器 fetch/XHR 其实两者都能发 body，差异主要在语义、缓存、幂等约束与 CSRF 面。

【一句话背诵】4 位看位（401 没登录、403 有身份无权限、502/504 网关侧），GET 幂等可缓存、POST 走 body。

##### N7. HTTPS 握手过程？为什么是"非对称加密 + 对称加密"混合？

【面试回答】TLS 握手（以 TLS1.2 RSA 密钥交换为例）：ClientHello 带支持的套件与随机数→ServerHello 选定套件 + 证书（含服务器公钥）→客户端验证证书链（根 CA 签名、域名、有效期、是否吊销）→生成预主密钥用公钥加密发送→双方用三个随机数算出相同的对称会话密钥→切换加密通信。之所以混合：非对称加密（RSA/ECDHE）安全但计算贵，不适合大量数据；对称加密（AES-GCM）便宜但需要安全分发密钥——非对称正好用来安全地协商对称密钥。TLS1.3 精简为 1-RTT，废弃 RSA 密钥交换全用 ECDHE（前向保密：长期私钥泄露也无法解密历史会话，这是 RSA 密钥交换的硬伤）。证书的意义是防中间人——公钥谁都能生成，CA 签名证明"这把公钥真的属于这个域名"。

【一句话背诵】非对称只协商密钥、对称跑数据；证书防中间人，1.3 用 ECDHE 实现前向保密。

##### N8. Cookie、Session、Token(JWT) 与跨域 CORS？

【面试回答】Cookie 是浏览器端的键值对，随同源请求自动携带，可设 HttpOnly（防 XSS 读取）、Secure、SameSite（防 CSRF）。Session 把状态存服务端、Cookie 只放 session id，集中可控但扩容要共享存储。JWT 把状态自包含进令牌（header.payload.signature 三段 Base64URL + 签名），服务端不存会话、验签即可，天然适合无状态水平扩展——我项目后端就是无状态 JWT；代价是签发后难撤销（需要黑名单/短过期+refresh）、payload 不能放敏感数据（Base64URL 只是编码不是加密，谁都能解开看）。跨域是浏览器同源策略：协议/域名/端口任一不同即跨域，服务端配 Access-Control-Allow-Origin 等响应头授权，预检 OPTIONS 处理非简单请求；面试常问"带 cookie 的跨域"：Allow-Credentials true + Allow-Origin 明确写域名（不能是*）+ 前端 withCredentials。

【一句话背诵】Cookie 存客户端随请求，JWT 自包含适合无状态；跨域靠服务端 CORS 头，带凭据就不能用通配。
