### 十一、操作系统高频必考（进程线程 / 内存管理 / IO）

##### O1. 进程和线程的区别？为什么线程切换比进程快？

【面试回答】进程是资源分配的基本单位：独立虚拟地址空间、文件描述符表、信号处理表，隔离性强。线程是 CPU 调度的基本单位：同进程内线程共享地址空间、堆、fd 表，各自只有栈、寄存器上下文和线程局部存储。切换代价差异根源在地址空间：进程切换要换页表基址（CR3）并导致 TLB 失效，后续访存重新翻译；线程共享同一地址空间，不换页表，TLB 保留。所以线程轻量、通信直接（共享内存，但要自己加锁），进程重、通信要走 IPC。一个 Java 进程里就跑着 GC 线程、JIT 线程、业务线程——线程数不是越多越好，上下文切换成本会吃掉吞吐。

【一句话背诵】进程管资源、线程管调度；换页表 TLB 失效是进程切换贵的根源。

##### O2. 协程（用户态线程）和线程的区别？

【面试回答】线程由内核调度，切换陷入内核态（系统调用），栈默认 MB 级。协程完全在用户态调度：切换只是保存少量寄存器和栈指针，不进内核，微秒级；栈可小到几 KB，轻松开十万个，因此适合高并发 IO 密集场景（Go 的 goroutine、Kotlin 协程、Python asyncio）。协作式调度意味着协程内不能跑长阻塞 CPU 任务，否则独占线程；阻塞 IO 要交给事件循环（epoll）或 runtime 自动 park（Go 的 netpoller 会在系统调用时把 P 让给别的 G，这是它透明的关键）。Java 21 的虚拟线程就是同一思想：JDK 内调度，阻塞时卸载载体线程，让"一请求一线程"模型在海量并发下重新可行。

【一句话背诵】协程用户态调度、切换不进内核、栈小量大；怕阻塞，配合事件循环/虚拟线程用。

##### O3. 用户态和内核态切换发生在什么时候？系统调用为什么慢？

【面试回答】切进内核的三类时机：系统调用（主动 int 0x80/syscall 指令）、中断（时钟、IO 完成）、异常（缺页）。慢的原因：一是上下文保存恢复寄存器；二是权限切换与流水线刷新、 speculative 执行防御开销；三是内核可能把 CPU 分给别的进程导致缓存污染；四是频繁小调用累积。这也是"减少系统调用"的工程依据：批量 read/write、sendfile 零拷贝（省用户态缓冲区间来回拷）、epoll 一次 wait 管万连接而不是每 fd 一次 poll、NIO 直接缓冲区。我项目里批量写库本质就是"把万次网络/系统开销摊成几十次大请求"。

【一句话背诵】系统调用/中断/异常进内核；慢在切换与缓存污染，零拷贝与多路复用都在减切换。

##### O4. 虚拟内存和缺页中断的流程？

【面试回答】每个进程看到独立连续虚拟地址空间，MMU 按页表翻译成物理页，带来三大好处：隔离安全、可交换（物理内存不够时把不活跃页换出到磁盘=swap）、按需分配（fork 后 COW）。访问未映射或已换出的页触发缺页中断：CPU 陷入内核→查 VMA 判断地址是否合法→合法则分配物理页、从磁盘读入或清零、更新页表，非法则 SIGSEGV（段错误）。malloc 大块内存实际只建 VMA，首次写入才缺页拿到物理页；mmap 文件映射后读页走文件 IO。COW：fork 不真复制页，只复制页表并标只读，任一方写入时才复制该页——这正是 Redis RDB 快照 fork 的底层机制。

【一句话背诵】虚拟地址经 MMU 查页表，缺页即内核补页；fork/mmap 惰性复制全靠 COW。

##### O5. 常见的内存管理策略：分页、分段、伙伴系统、slab？

【面试回答】分段按逻辑（代码/数据/栈）长度不等，会产生外部碎片；分页把空间切成固定页（4KB），逻辑连续物理离散，消灭外部碎片、留下内部碎片（最后一页浪费），多级页表（x86-64 4~5 级）解决大地址空间页表本身占内存的问题，TLB 缓存翻译加速。内核管理物理页用伙伴系统：按 2^k 页成组分配、合并回收，快但粒度粗（小对象浪费）；slab/SlUB 在页之上按对象大小建缓存池（kmalloc 的 8 种 size class 等），同类对象复用免重复构造，还做着色防伪共享。应用层：Java 堆是 JVM 在操作系统上申请的连续大段，由 JVM 自己再细分代和 Region 管理——面试能把"OS 分页→JVM 分代"串起来讲是亮点。

【一句话背诵】分页固定粒度消外碎片，多级页表 + TLB 提速；伙伴管页、slab 管对象。

##### O6. 死锁的四个必要条件与预防策略？

【面试回答】互斥（资源同时只能一人持有）、持有并等待（拿着 A 要 B 不先放 A）、不可剥夺（只能持有者自愿释放）、循环等待（排队成环）。破坏任一即可预防：破坏持有并等待→一次性申请全部资源或先释放再申请；破坏不可剥夺→抢占式（银行家算法思路，超时被夺）；破坏循环等待→全局资源定序，所有人按同一顺序拿锁（工程最常用：我实习项目里多志愿者并发领任务按任务 id 升序加锁）。避免策略：银行家算法事前检查分配后系统是否仍在安全状态，开销大实际少用。检测：资源分配图化简/等待图找环，DBMS 用 wait-for graph 回滚受害者，Java 里 jstack 会直接打印 Found deadlock。

【一句话背诵】四条件缺一不可；工程首选"统一拿锁顺序"，检测靠等待图找环。

##### O7. 中断、轮询与 IO 多路复用（select/poll/epoll）？

【面试回答】硬件 IO 用中断驱动：数据就绪 CPU 收到 IRQ 再处理，避免傻等；但海量连接下每次中断都唤醒内核与进程代价高。编程侧阻塞 IO 让线程挂起等内核通知；多路复用让一个线程同时监听多个 fd：select（1024 上限、每次全量拷贝 fd 集、内核 O(n) 遍历）、poll（链表去掉 1024、仍全量遍历）、epoll（红黑树管理监听集合一次注册，就绪链表 + 回调只返回活跃 fd，O(活跃数)；LT 水平触发安全默认、ET 边沿触发减少唤醒必须一次读完）。这就是 Redis/Nginx/Netty 单线程扛万级连接的原因，也把 O3 的"减少系统调用"落到实处。

【一句话背诵】中断替代轮询省 CPU，epoll 用红黑树 + 就绪回调把"遍历所有 fd"变成"只取就绪"。

##### O8. 并发编程的 OS 视角：互斥锁、信号量、条件变量？

【面试回答】互斥锁是二元信号量的特化：加锁失败线程进等待队列休眠，内核负责排队与唤醒，一次只放一个。信号量计数 N，可同时放 N 个（资源池、连接池限流即它），P/V 操作。条件变量必须搭配互斥锁使用：wait 原子地"放锁 + 睡到等待队列"，唤醒后重新抢锁再继续，因此循环检查条件（防虚假唤醒）——这与 Java 里 while(!cond) wait() 完全同源，是"语言 API 背后是 OS 原语"的标准答法。自旋锁适合临界区极短且不睡眠场景（内核态），Java synchronized 的轻量级锁自旋就是借用它思想。能说出 futex（快路径用户态原子、慢路径才进内核排队）是加分项，Linux 上 mutex/条件变量底层都是 futex。

【一句话背诵】锁排队、信号量计数放行、条件变量先睡后醒再抢锁，Java wait/notify 即其映像。
