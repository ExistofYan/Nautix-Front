# 简历项目 STAR 改写稿（基于源码核验版）

> 说明：本稿全部量化数据都以 shipsensor / nautix-frontend / ship 三个代码库的源码实测为准，未采信任何过时 README。文末附「数据核验清单」，列出每处数字的证据强度，以及原简历中建议删除或改写的表述。

## 一、简历版条目（可直接粘贴，STAR 隐式结构）

### NAUTIX —— 海事物联网实时数据流与态势感知平台（GitHub: TongYan05/NAUTIX）｜2026.06–2026.09｜核心开发

技术栈：Java 17、Spring Boot 3、MyBatis-Plus、MySQL 8、Vue 3、TypeScript、ECharts、CesiumJS

- **亿级时序写入管线**：针对万艘船舶 × 17 类传感器持续高频上报、逐行 INSERT 无法收敛的瓶颈，设计有界队列（ArrayBlockingQueue，100 万容量）削峰的生产者-消费者架构，由 16 个专职写线程按 5 万行/批拉取并以多值 INSERT + 独立短事务提交，完成 2.6 亿+ 行历史时序回填，并支撑约 8.6 万行/天的实时增量写入持续服务。
- **大表写入路径优化**：亿级 sensor_data 表采用"先灌数、后建索引"策略，避免持续页分裂与索引维护开销，(ship_id, recorded_at) 复合索引单次构建约 6.5 分钟；查询侧用主键倒序替代无索引时间列排序，将时间窗换算为主键下界收敛扫描范围，配合行数上限强制，使统计接口稳定走索引返回。
- **查询性能治理**：通过 EXPLAIN 定位航线数据 N+1 缺陷——10 万+ 次逐行 route_point 查询重构为 2 次全量加载 + ConcurrentHashMap 内存分组缓存（启动期 @PostConstruct 预热），接口响应从约 2s 降至约 200ms；亿级表行数统计改读 information_schema 估算值，彻底消除 COUNT(*) 全表扫描。
- **规则驱动告警引擎**：实现阈值比较算子 + 持续时长双条件的告警判定，对异常读数做"事件开合"聚合（OPEN 事件合并进持续中的 ALERTING 记录，恢复后归档时长与峰值指标），内置 80 条种子规则覆盖 17 类传感器；配套 22 个传感器生成器与 14 组跨传感器物理耦合公式（RPM→排温/燃耗/振动联动），保证告警链路可被仿真数据端到端验证。
- **零模型依赖的本地智能问答**：将自然语言提问经关键词 + 英文词边界正则路由至 9 个业务查询域与生活助手域，命中预置参数化 SQL 并强制 LIMIT 行数上限，端到端响应约 1s；全链路不依赖任何外部 LLM，回答 100% 来自真实库查询结果，从机制上杜绝幻觉且可离线运行。
- **前端可视化与信息架构**：独立实现 Vue 3 + TypeScript 全部界面（54 视图、101 组件、29 处 ECharts 图表模块），未套用任何后台模板；自研 SVG 航海图以等经纬投影渲染万艘船舶位置，通过服务端过滤、视口包围盒裁剪与单帧 800 船渲染上限将首屏渲染数据量压缩约两个数量级；另实现 CesiumJS 三维地球数字孪生页。
- **安全与国际化工程**：后端 19 个 Controller、119 个 REST 端点，Spring Security + jjwt 无状态鉴权，自定义 401/403 JSON 端点保证 API 语义化返回；前端 Axios 拦截层在 401 时自动清理会话并引导重登（杜绝白屏假死）；自研零依赖 i18n 字典（361 组双语键，en 为基准键集、zh 以 Record＜MsgKey, string＞ 强制编译期对齐），全站一键中英切换。

### NEXMAR —— 船队调度与资源管理系统｜2026.03–2026.06｜全栈开发（压缩版）

技术栈：Spring Boot、MyBatis-Plus、MySQL、Druid、Vue 3、Docker、Nginx

- **嵌套数据建模**：对船员多证书场景用 @TableName(autoResultMap) + JacksonTypeHandler 将证书列表落为单列 JSON 数组，以"附属数据不独立检索"为约束避免多表 JOIN，前端配套完成嵌套字段的增删改编辑器。
- **统一列表服务范式**：5 个业务模块的服务端分页接口统一实现动态条件构造、count>100 大页限流、排序字段白名单校验（防排序注入），配合 PaginationInnerInterceptor（jsqlparser 自动 COUNT 改写），支撑船舶/船员/航次/分配/用户 5 表 37 个端点复用同一套查询防护逻辑。
- **压测数据与部署**：基于 DataFaker 实现百万级用户数据分批构造（1000 条/批 + rewriteBatchedStatements 批重写）用于压力验证；完成 Spring Boot 应用 Dockerfile 与前后端 Nginx 反向代理部署，排查并修复 proxy_pass 路径截断导致的 404 线上故障。

### 大模型辅助的海洋结构有限元自动化分析（本科科研方向）｜2026.04–2026.09

技术栈：Python、Julia、Abaqus/CAE、Gridap、StarCCM+（课程环境）、LLM 辅助编码

- **LLM 辅助参数化建模管线**：将船体/桥梁结构的几何参数与载荷工况以提示工程描述给大模型，生成 Abaqus/CAE Python 脚本（草图→布尔成型→网格→分析步→载荷→Job 提交全链路），复现双拱肋桥、受压锥体等参数化模型，把手工 GUI 建模沉淀为可重放、可版本管理的代码。
- **自研 Julia 有限元求解与三重数值校验**：基于 Gridap 对局部船体外板建立二阶三维六面体实体模型（含真实板厚、四边固支、静水压力 + 附加压力载荷），编写自动校核闭环——载荷合力与解析值 rtol 1e-8 一致、内/外力功能量守恒误差 < 1e-6、网格加密关键位移差 > 5% 即触发再细化警告，输出位移/Von Mises/双向应力云图、放大变形图与 VTU/CSV 结果文件。
- **双船对比批处理**：以参数化外形同时驱动货船与巡逻船两组外板分析，自动生成校核摘要（summary.txt），形成"参数输入→求解→校核→报告"的单人可维护仿真工作流，为后续接入型线图纸→模型自动生成的完整链路打下代码基础。

## 二、显式 STAR 版（面试口述讲稿骨架）

### NAUTIX（约 3 分钟版）

**Situation**：毕业设计要做船东运营台：1 万艘模拟船舶持续上报引擎、燃油、GPS 等 17 类传感器遥测，数据量最终到达 2.6 亿行级别；单机 MySQL 上逐行写入吞吐不足、统计查询动辄全表扫描，前端图表也扛不住万级实体渲染。

**Task**：我一个人负责全栈，需要在不引入 Kafka/Redis 等额外中间件的前提下，让写入、查询、告警、可视化四条链路都在单机可复现地跑通，并做出有真实数据语义的演示系统。

**Action**：写入侧把生成与落库解耦成"有界队列（100 万容量）+ 16 个写线程 × 5 万行多值 INSERT + 每批独立事务"的管线，先灌数后建索引；查询侧用 EXPLAIN 找到航线 N+1，改成两次全量查询 + 内存分组缓存，亿级表 COUNT 换成 information_schema 估算、时间窗换算主键下界；告警侧实现阈值 + 持续时长双条件的规则引擎和事件开合聚合；AI 问答做成本地意图路由直接生成参数化 SQL；前端自研 SVG 航海图用视口裁剪 + 渲染上限压数据量。

**Result**：完成 2.6 亿行回填、实时约 8.6 万行/天稳定写入；航线接口 2s → 200ms；80 条规则在耦合仿真数据上端到端触发告警；问答端到端约 1s 且零外部依赖；119 个接口全部 JWT 保护、401 语义化；54 页全站中英切换编译期保证键对齐。项目沉淀了我对"高写入压力 + 大表查询 + 单机约束"三角权衡的完整手感。

**追问预案**：为什么不用 Redis/Kafka（单机演示 + 依赖最小化，用内存队列换吞吐验证同样成立）；为什么多值 INSERT 不用 MyBatis batch（减少 JDBC 往返、单语句提交日志开销可控）；数据一致性怎么保证（事务批 + 幂等重灌 + 启动期计数校验）。

### NEXMAR（约 90 秒版）

**S**：本科第二个系统课设，船公司要管理船舶、船员、航次与人员分配，数据要在多个模块间关联且能上线演示。

**T**：独立完成后端 API、前端界面和上云部署全链路。

**A**：船员证书这种一对多附属数据用 JSON 列 + TypeHandler 做嵌套建模，避免多表 JOIN；五个模块的分页接口统一做动态条件、大页限流和排序字段白名单；用 DataFaker + 批量提交造百万级测试数据验证压力；Dockerfile + Nginx 反向代理上线，期间排查了 proxy_pass 路径截断导致的 404。

**R**：5 模块 37 端点稳定运行，前端全部面板走服务端分页；这次踩坑让我理解了 MyBatis-Plus 分页插件的 COUNT 改写机制和 Nginx location 转发语义——这两个点在后来 NAUTIX 的开发里直接复用。

### FEA 项目（约 2 分钟版）

**S**：本科船舶与海洋工程专业背景，传统 Abaqus 建模高度依赖手工 GUI，改一次参数要重画一遍网格；同时我判断大模型已经能生成结构化工程脚本。

**T**：验证"自然语言/参数 → 建模代码 → 求解 → 自动校核"的自动化科研管线，并把结果做成可信的有限元分析。

**A**：用提示工程让 LLM 生成 Abaqus/CAE Python 脚本，复现双拱肋桥、受压锥体等模型；在 Julia Gridap 里自研二阶六面体外板求解器，内置三重数值校核（合力 rtol 1e-8、能量守恒 < 1e-6、网格加密 5% 收敛阈值）；货船/巡逻船双船并行批处理，自动生成云图、VTU 和摘要报告。

**R**：建模从"手工 GUI 小时级"变为"脚本重放分钟级"，且每次结果都有能量/网格双重背书；下一步计划把船体型线图输入接进来，实现图纸→几何→网格→求解的端到端。这段经历是我"AI + 工程仿真"交叉方向的证据，也是我想进 AI 应用工程岗的动机来源。

## 四、专业技能栏修订建议

- 开发语言：Java（并发编程、JVM 内存模型与调优）、SQL、TypeScript、Python

- 存储与数据：MySQL（InnoDB 索引与事务原理、执行计划分析、亿级大表写入与查询优化）、Redis（数据结构、持久化、缓存一致性）
- 前端工程：Vue 3 + TypeScript、Vite、ECharts、CesiumJS、零依赖 i18n 方案
- 工程与部署：Git、Docker、Nginx 反向代理、Linux、云上部署与线上故障排查
- 交叉方向：LLM 辅助工程脚本生成、Julia/Gridap 有限元数值校核
